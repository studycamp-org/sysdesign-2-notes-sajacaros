## 더 찾아본 것 (선택)

### 위치 이력 저장: Cassandra vs 메시지 큐 → 배치 → 데이터 레이크

**결론**: S1처럼 이력을 ML 학습용으로만 쓰면 큐 → 레이크가 맞다. 앱에서 사용자가 자기 이력을 바로 조회하는 기능(예: "내 이동 기록 보기")이 생기면 Cassandra가 필요해진다.

#### RDB 감각으로 보기

- **Cassandra**: 샤딩이 처음부터 들어 있고, 인덱스가 사실상 하나뿐인 거대한 테이블.
  ```sql
  CREATE TABLE location_history (
    user_id bigint,
    ts      timestamp,
    lat double, lng double,
    PRIMARY KEY ((user_id), ts)   -- user_id로 노드를 정하고, 그 안에서 시각순 정렬
  ) WITH default_time_to_live = 2592000;  -- 30일 지나면 자동 만료
  ```
  - 쓰기가 빠른 이유: 같은 행을 찾아 고치지 않는다. 로그에 덧붙이고 메모리에 쌓았다가 파일로 한꺼번에 내린다. 노드를 늘리면 쓰기 처리량도 거의 비례해 는다.
  - RDB와 다른 점: 파티션 키를 낀 조회(`WHERE user_id = ? AND ts > ?`)만 빠르다. "강남에 있던 사람 전부" 같은 조회는 사실상 불가, JOIN 없음. 테이블을 질의 패턴에 맞춰 설계한다.
- **Kafka → 배치 → 레이크**: 일 단위 파티션 테이블을 싼 창고에 두고 30일 지나면 `DROP PARTITION` 하는 것과 비슷하다.
  - Kafka: 디스크에 쌓이는 추가 전용 로그. 보관 기간 동안은 컨슈머가 죽었다 살아나도 이어서 읽는다.
  - 배치: 몇 분~한 시간마다 Parquet(열 단위 압축 파일)로 변환.
  - 레이크: S3 등 객체 저장소에 `dt=2026-10-25/hour=23/` 형태의 날짜별 폴더로 저장.
  - 조회: Spark·Trino·Athena로 SQL. 결과가 수 초~수 분 뒤에 나와 실시간 조회용이 아니다.

#### S1 기준 비교

| 기준 | Cassandra | 큐 → 레이크 |
|---|---|---|
| 초당 6.7만 쓰기 (피크 20만) | 노드 수로 감당 | Kafka가 받고 레이크에는 묶어서 씀. 여유 있음 |
| 조회 패턴 | 사용자 한 명의 기간 조회를 ms 단위로 | 대량 분석을 분 단위로. ML 학습에 맞음 |
| 30일 보관 | 행마다 TTL. 삭제 표시(tombstone)가 쌓여 compaction 튜닝 필요 | 날짜 폴더 삭제나 수명 주기 규칙. 거의 공짜 |
| 저장 용량 (원본 약 17TB) | 복제 3벌이면 약 50TB 이상, SSD 노드 수십 대 (대략) | Parquet 압축 후 수 TB, 객체 저장소 단가 (대략) |
| 특정 사용자 이력 삭제 | 파티션 하나 삭제로 쉬움 | 어려움. 그 사용자가 섞인 파일을 전부 다시 써야 함 |
| 운영 부담 | 클러스터, compaction, repair 등 전담 지식 필요 | Kafka 운영 + 배치 작업. 관리형 서비스면 가벼움 |
| 장애 시 | 노드 일부가 죽어도 복제본으로 계속 씀 | Kafka 보관 기간 안에 배치가 따라잡으면 유실 없음 |

용량·비용은 압축률과 복제 수에 따라 크게 달라지는 대략적인 수치다. 그래도 자릿수가 다르다는 점은 유지된다.

#### 놓치기 쉬운 점: 사용자별 삭제

- S1은 위치 공유가 opt-in이라, 공유를 끄거나 탈퇴하면서 기록 삭제를 요청하면 지워야 할 수 있다(개인정보보호법).
- Cassandra는 `DELETE ... WHERE user_id = ?` 한 줄이면 된다. 일반 Parquet 레이크는 30일치 파일을 다시 써야 한다.
- 해결책: ① Iceberg·Delta Lake 같은 테이블 포맷을 얹어 `DELETE FROM ... WHERE user_id = ?` 사용 ② 삭제 요청을 모아 주기적으로 일괄 삭제하고, 그 사이에는 학습 데이터에서 제외(법적 요건 확인 필요)

#### 둘 다 쓰는 경우

이력이 핵심 기능이면(예: S3 같이달려, 활동 기록 영구 보관·내보내기) `Kafka → Cassandra(앱 조회용) + 레이크(분석용)` 구성이 흔하다.

#### 직접 해볼 것

- 레이크: 파이썬으로 가짜 위치 데이터를 Parquet로 쓰고 DuckDB로 `SELECT` 해보기. 서버 없이 SQL 그대로.
- Cassandra: `docker run cassandra`로 띄워 위 테이블을 만들고, `WHERE lat > 37.5` 같은 조회를 실행해 에러를 직접 겪어보기.
