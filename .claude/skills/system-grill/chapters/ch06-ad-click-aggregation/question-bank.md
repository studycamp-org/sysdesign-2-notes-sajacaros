# 질문 은행 (4문항, 20~30분)

**핵심 질문은 정확히 4개다.** 문항이 적은 만큼 질문당 약 5~6분. 묶음 질문은 소항목 최대 2개.
교재의 나머지 주제(질의 API 모양, 원시·집계 데이터 스키마, 스타 스키마 필터링, 맵/집계/리듀스 노드 구성, 카산드라 가상 노드, 토픽 물리적 샤딩, 모니터링 지표)는 질문으로 내지 않는다.
답에 나오면 기록하고, 아키텍처와 핵심 흐름은 마무리 단계에서 진행자가 그린다.

| 단계 | 질문 |
|---|---|
| 요구사항 | Q1 규모 추정 |
| 초안 설계 | **Q2 저장할 데이터와 집계 경로 (묶음) ★** |
| 상세 설계 | Q3 시간과 집계 윈도 (묶음) · **Q4 전달 보장과 정확성 지키기 (묶음, 돌발)** |

각 항목: **질문** / **선택지**(예시, 다른 답도 받음) / **꼬리 질문**(빈약하거나 충돌할 때만, 최대 1회) / **좋은 근거의 신호**(피드백 기준, 답하기 전에는 보여주지 않음).

시나리오별 계산 정답 (진행자 확인용, 하루 ≈ 10⁵초, 집계 노드·파티션 1개 = 초당 1만 이벤트, 사본 제외):

| 시나리오 | 평균 / 최대 QPS | 집계 노드 수 (최대 기준) | 원시 하루 / 보관 전체 | 따로 볼 숫자 |
|---|---|---|---|---|
| 교재 | 10⁹ ÷ 10⁵ = **10⁴** / × 5 = **5×10⁴** | **5대** (3년 뒤 트래픽 2배면 10대) | 10⁹ × 0.1KB = **100GB** / 한 달 **3TB** | 1분 집계 결과 행 수 상한 = 광고 200만 × 1,440분 ≈ **2.9×10⁹**/일 (실제로는 클릭 있는 광고만) |
| S1 | **10⁴** / **5×10⁴** | **5대** | **100GB** / 1년 **36.5TB** | 돌발: 3일 치 재계산 = 3×10⁹건(300GB). 노드 5대면 6×10⁴초 ≈ **17시간**, 50대면 ≈ **1.7시간** |
| S2 | 2×10⁸ ÷ 10⁵ = **2×10³** / 평소 최대 **10⁴**, 하프타임 **≈ 31만** | 평소 **1대**, 하프타임 **31대**. 그런데 그중 30만은 **광고 하나 = 파티션 하나** → 한 파티션·한 노드에 **30배** 초과 | 평소 **20GB** + 하프타임 30만 × 300초 × 0.1KB = **9GB** / 1년 평소 기준 **7.3TB** | 한 파티션 적체: (30만 − 1만) × 300초 ≈ **8,700만 건**. 1만/s로 다 비우는 데 ≈ **2.4시간** |
| S3 | 3×10⁹ ÷ 10⁵ = **3×10⁴** / × 3 = **9×10⁴** | **9대** | 3×10⁹ × 0.2KB = **600GB** / 90일 **54TB** | 늦게 오는 클릭 5% = 하루 **1.5억 건**. 워터마크 15초면 거의 다 윈도 밖 → 실시간 결과가 **약 5% 적다**. 돌발: 36억 건 → 720GB/일, 최대 10.8만 → 11대 |
| S4 | 5×10⁸ ÷ 10⁵ = **5×10³** / × 5 = **2.5×10⁴** | **3대** | **50GB** / 2년 **36.5TB** | 최대 때 10초 동안 반영 안 된 클릭 2.5만 × 10 = 25만 건 × 500원 ≈ **1.25억 원**(1분이면 7.5억 원). 하루 총 집행 ≈ 2,500억 원. 돌발: 노드 1대 몫(≈ 8,300/s) × 240초 ≈ 200만 건 ≈ **10억 원** 미반영 |

(0.1KB는 교재 값이고 압축 전이다. 원시 데이터를 파케이·ORC 같은 열 지향 형식으로 S3에 두면 몇 배 준다. 카산드라 등에 사본 3개를 두면 ×3. Q1·Q2 꼬리 질문에서 쓴다.)

## 요구사항

### Q1. 규모 추정
- **질문**: 평균·최대 QPS, 필요한 집계 노드(파티션) 수, 원시 데이터의 하루 저장량과 보관 기간 전체 저장량을 직접 계산하세요. 이 시스템에서 가장 먼저 한계에 닿는 것은 무엇인가요? (쓰기 처리량 / 저장 용량 / 집계 지연 / 특정 광고 쏠림(핫스팟) / 정확성(중복·늦은 이벤트) / 그 밖)
- **좋은 근거의 신호**: 평균 QPS = 하루 클릭 ÷ 10⁵, 최대는 시나리오 배수를 곱한다. 노드·파티션 수는 **평균이 아니라 최대** 기준이고, 3년 뒤 2배(교재) 같은 여유를 생각한다 — 파티션 수는 나중에 늘리면 같은 `ad_id`가 다른 파티션으로 가므로 **처음에 넉넉히** 잡는다(교재). 원시 저장량은 크지 않다(교재 100GB/일) → 이 장의 진짜 한계는 용량보다 **정확성과 지연**이라는 것을 보면 좋다. S2는 **전체 QPS보다 광고 하나의 QPS**가 한계(한 파티션 30배 초과), S3는 늦은 5%가 곧 청구 오차, S4는 지연이 곧 돈(초당 미반영 금액)이라는 것을 숫자로 연결하면 좋다.
- **꼬리 질문**: "파티션 수를 지금 노드 수에 딱 맞춰 정했다가 1년 뒤 늘리면 무슨 일이 생기나요?" / "최대 QPS 기준으로 노드를 잡았는데, 그래도 노드 하나가 넘칠 수 있는 경우는요?"

**▶ 요구사항 체크포인트**

## 초안 설계

### Q2. 저장할 데이터와 집계 경로 (묶음) ★핵심
- **질문**:
  1. 무엇을 저장하나요? A) 원시 데이터만(질의할 때 집계) B) 집계 결과만 C) **둘 다**(원시는 백업·재계산용, 집계는 질의용) D) 그 밖. 각각 어떤 저장소에 두나요?(카산드라 같은 쓰기 중심 NoSQL / S3 + 열 지향 형식 / 관계형 DB / OLAP DB)
  2. 집계는 어떤 경로로 하나요? A) **스트림 처리**만 — 카파 아키텍처(재처리도 같은 엔진으로) B) **일괄 처리**만(맵리듀스·스파크로 주기적으로) C) **람다 아키텍처**(스트림으로 빠른 값 + 일괄로 정확한 값, 코드 두 벌) D) OLAP DB(클릭하우스·드루이드)에 넣고 질의 시점 집계(교재 대안 설계) E) 그 밖
- **좋은 근거의 신호**: 원시만 두면 질의마다 대량 스캔이라 느리고, 집계만 두면 **버그가 났을 때 재계산할 원본이 없다**(교재: 둘 다 저장 권장). 원시는 쓰기 중심·시간 범위 조회라 카산드라나 S3+열 지향 형식, 집계 결과는 읽기 중심. 표 6.17 — 일괄 처리는 처리량, 스트리밍은 처리량 + 지연이 기준이고 입력에 경계가 없다. 람다는 두 경로를 유지해야 하는 부담, 카파는 **단일 스트림 엔진으로 실시간 처리와 재처리를 모두** 한다(교재 선택). 재처리할 때는 원시 데이터를 읽어 **재계산 전용 집계 서비스**로 보내 실시간 경로와 간섭하지 않게 한다(그림 6.11). 시나리오 연결: S1 1년 원시 보관이 재계산의 근거, S2 집계 노드를 탄력적으로 늘리는 스트림, S3 늦은 5% 때문에 "정확한 값은 일괄로 다시"라는 람다식 유혹, S4 10초 지연이라 스트림 필수 + 정확한 청구는 따로.
- **세부 질문** (2번에서 고른 방식에 맞는 것 **하나만**, 같은 질문 안에서):
  - **스트림(카파)**: "집계 로직에 버그가 있었던 걸 3일 뒤에 알았습니다. 그 3일 치를 어떻게 다시 계산하고, 그동안 실시간 집계는 어떻게 되나요?"
    - 신호: 원시 데이터 저장소(또는 카프카 보관 기간 안이면 카프카)에서 다시 읽어 재계산 전용 집계 서비스로 → 결과를 두 번째 메시지 큐 → 집계 결과 DB에 덮어쓰기(그림 6.11). 실시간 경로와 자원을 나눈다. 카프카 보관 기간(예: 7일)보다 오래된 구간은 원시 DB가 필요하다.
  - **일괄**: "요구사항이 '분 단위 지연'인데, 일괄 작업 주기는 얼마로 잡나요? 그 주기 사이에 대시보드는 무엇을 보여 주나요?"
    - 신호: 주기를 짧게 하면 사실상 마이크로배치. 작업 시작 비용·겹침·늦은 데이터 재처리를 짚는다. 과금 확정처럼 지연이 허용되는 곳에는 일괄이 맞을 수 있다.
  - **람다**: "스트림 결과와 일괄 결과가 다르면 사용자는 어느 값을 보나요? 같은 집계 로직을 두 벌 유지하는 비용은 어떻게 줄이나요?"
    - 신호: 최근 구간은 스트림 값, 확정된 구간은 일괄 값으로 덮어쓰기. 두 코드가 어긋나는 위험(교재가 지적한 단점). 교재의 '조정'은 람다처럼 보이지만 **결과를 만드는 경로가 아니라 비교·검증**이라는 차이를 아는지.
  - **OLAP 질의 시점**: "상위 100개 광고를 매분 질의하면 OLAP DB는 매번 무엇을 스캔하나요? 늦게 온 이벤트는요?"
    - 신호: 원시를 넣는 순간 늦은 이벤트도 자연히 반영되는 장점. 대신 질의 부하·비용, 사전 집계(머티리얼라이즈드 뷰·롤업)로 보완. 중복 제거는 따로 필요.
- **꼬리 질문**:
  - 공통: "집계 결과 DB가 30분 동안 쓰기를 못 받으면, 그 사이 집계 결과는 어디에 있나요?" (→ 집계 결과도 메시지 큐를 거치는 이유, 그림 6.11·6.28)
  - "원시 데이터를 1년(또는 시나리오 보관 기간) 들고 있는 비용과, 안 들고 있을 때 잃는 것은요?"

**▶ 초안 설계 체크포인트**

## 상세 설계

### Q3. 시간과 집계 윈도 (묶음)
- **질문**:
  1. 어느 시각으로 집계하나요? A) **이벤트 시각**(클릭이 일어난 시각, 클라이언트·광고 서버가 찍음) B) **처리 시각**(집계 서버가 처리한 시각) C) 섞어서(예: 이벤트 시각으로 집계하되 너무 이상한 값은 처리 시각으로) — 그리고 늦게 오는 이벤트를 위한 **워터마크**는 몇 초로 하나요? 워터마크를 지나서 온 이벤트는 어떻게 하나요?
  2. 두 요구사항을 어떤 윈도로 집계하나요? ① 광고별 매분 클릭 수 ② 지난 M분 상위 100개 광고 — 텀블링(고정) / 호핑 / 슬라이딩 / 세션 중 무엇을, 왜? 상위 100개는 어떻게 계산하나요?
- **좋은 근거의 신호**: 표 6.18 — 이벤트 시각은 **더 정확**하지만 클라이언트 시각이 틀리거나 조작될 수 있고, 처리 시각은 안정적이지만 **늦게 온 이벤트가 엉뚱한 윈도에 들어가** 부정확하다. 교재는 정확성이 중요하므로 **이벤트 시각 + 워터마크** 추천. 워터마크가 길면 늦은 이벤트를 더 잡지만 결과가 늦어지고, 짧으면 반대. 아주 늦은 이벤트를 위해 시스템을 복잡하게 만드는 건 ROI가 낮고 **하루 마감의 조정으로 보정**한다(교재). 윈도: 매분 클릭 수 = **텀블링**(그림 6.15), 지난 M분 상위 N개 = **슬라이딩**(그림 6.16, 엄밀히는 1분씩 움직이는 호핑 — 1분 텀블링 결과를 M개 합치면 된다, 부록). 상위 100개는 집계 노드마다 힙으로 지역 상위 100 → 리듀스에서 합친다(교재 밖 세부: 지역 상위 N만 합치면 틀릴 수 있어 광고별 수를 모두 넘기거나 넉넉히 넘긴다). 시나리오 연결: S3 단말 시계 오차·조작 + 24시간 늦은 5%(이벤트 시각을 그대로 믿을 수 없고 워터마크로는 못 잡는다 → 서버 수신 시각과 비교해 보정, 늦은 건 일 정산 때 반영), S4 10초 지연(워터마크가 곧 지연, 짧게 가고 정산에서 보정), S2 지난 5분 상위 100에서 한 광고가 독식.
- **꼬리 질문**: "워터마크를 15초로 했을 때, 1시간 늦게 온 클릭은 오늘 청구서에 들어가나요? 들어가야 한다면 어디서요?" / "광고 서버가 클릭을 받은 시각을 이벤트 시각으로 쓰면 클라이언트 시각의 단점은 사라지나요? 무엇이 남나요?"

### Q4. 전달 보장과 정확성 지키기 (묶음, 돌발 상황 포함)
- **질문**: 먼저 시나리오 카드의 **돌발 상황**을 제시하고, 그 상황을 전제로 답하게 한다.
  1. 중복과 유실을 어떻게 막나요? A) 최소 한 번 + 중복 허용 B) 최소 한 번 + **멱등 처리**(이벤트 ID·오프셋으로 중복 제거) C) **정확히 한 번**(집계 결과 전송 + 오프셋 저장을 한 트랜잭션으로, 카프카 트랜잭션·플링크 체크포인트 등) D) 그 밖 — 오프셋은 **언제** 저장하나요?(다운스트림 응답 전 / 후)
  2. 결과가 틀리거나 멈췄을 때 어떻게 알고 바로잡나요? (조정(reconciliation), 재계산, 스냅숏과 복구, 핫스팟 노드 추가 할당, 지연·records-lag 모니터링 등)
  - 돌발 상황 때문에 앞의 결정 중 바꿀 것이 있나요?
- **좋은 근거의 신호**: 몇 퍼센트 차이가 수백만 달러이므로 교재는 **정확히 한 번** 권장. 중복 원인은 두 가지 — 클라이언트 재전송(악의적이면 광고 사기·위험 제어 컴포넌트) / 서버 장애로 업스트림에 오프셋을 못 알려 재소비(그림 6.17). 오프셋을 다운스트림 전송 **전에** 저장하면 장애 시 **유실**(그림 6.18), **후에** 저장하면 유실은 없고 중복 가능(그림 6.19) → 둘을 묶는 **분산 트랜잭션**(그림 6.20). 단, 오프셋 기반 정확히 한 번은 **파이프라인 안의 재처리 중복**만 막고 **클라이언트가 같은 클릭을 두 번 보낸 것**(S3 돌발)은 못 막는다 → 클릭 ID로 중복 제거(교재 밖). 결함 내성: 집계는 메모리라 노드가 죽으면 날아간다 → 오프셋 + 지난 M분 상위 N개 같은 **상태를 스냅숏**하고, 새 노드는 스냅숏 + 그 뒤 카프카 구간으로 복구(그림 6.26·6.27). 스냅숏 주기가 길면 복구가 길다(S4 돌발). 정확성: **조정** = 매일 원시 데이터를 이벤트 시각 순으로 일괄 집계한 값과 실시간 결과를 비교(그림 6.28). 버그는 **재계산**(그림 6.11)으로 덮어쓴다(S1 돌발). 핫스팟은 자원 관리자에게 노드를 더 받아 이벤트를 나눠 집계하고 원래 노드에서 합친다(그림 6.25) / 전역-지역 집계, 핫 광고 키에 접미사를 붙여 여러 파티션에 흩기(교재 밖)(S2 돌발). 재조정은 소비자가 많을수록 오래 멈추므로 사용량 적을 때, 혹은 토픽을 물리적으로 나눠 소비자 수를 줄인다.
