# 시나리오 카드

각 시나리오는 교재 기준안(하루 클릭 10억 건 · 광고 200만 개 · 평균 10,000 QPS, 최대 50,000 QPS · 이벤트 1개 0.1KB, 하루 100GB · 분 단위 집계와 지난 M분 상위 100개 광고 · 국가 등 필터 · 결과는 과금과 RTB에 쓰임 · 늦게 도착한 이벤트와 중복을 처리해야 함 · 종단 지연은 몇 분 안)과
일부러 다른 제약을 하나 이상 넣어서, 같은 질문이라도 다른 선택이 정당화되도록 만들었다.

목록을 보여줄 때는 `한 줄 요약`만 보여준다. 고른 뒤에 카드 전체를 보여준다.

계산 공통 가정(카드에 따로 없으면): 하루 ≈ 10⁵초, **클릭 이벤트 1개 ≈ 0.1KB**(교재), 사본은 따로 곱한다.
**평균 QPS** = 하루 클릭 ÷ 10⁵. **최대 QPS** = 평균 × 카드의 최대 배수.
**집계 노드 1대는 초당 1만 이벤트**, **카프카 파티션 1개도 초당 1만 이벤트**를 감당한다고 가정한다(교재 밖, 계산용).
`ad_id`로 파티션을 나누면 **광고 하나는 파티션 하나, 집계 노드 하나**로 간다.

---

## S1. 검색광고 — 검색 포털 키워드 광고 과금  (입문 / 교재와 가장 비슷함)

**한 줄 요약**: 검색 결과에 붙는 클릭당 과금(CPC) 광고. 하루 클릭 10억 건을 분 단위로 집계해 광고주 대시보드와 월말 청구서에 쓴다.

| 항목 | 값 |
|---|---|
| 클릭 | 하루 **10억 건**, 최대는 평균의 **5배** |
| 광고 | **200만 개** |
| 이벤트 | `ad_id, click_timestamp, user_id, ip, country` (0.1KB) |
| 질의 | 광고별 분 단위 클릭 수(국가·기기 필터), 지난 1분 상위 100개 광고 |
| 지연 | 집계 결과는 **몇 분 안**에 대시보드에 반영 |
| 보관 | 원시 데이터 **1년**(청구 분쟁 대응), 집계 결과 무기한 |
| 정확성 | 청구서 기준. 일 단위로 확정해 광고주에게 보여준다 |

**설계 포인트**: 교재 기준안을 그대로 따라가도 되는 시나리오. 대신 **원시 데이터를 1년 들고 있어야 하는 이유**(재계산·분쟁)와 그 비용을 의식하는지 본다.

**돌발 상황**: "집계 서비스 배포 하나에 버그가 있어 **3일 동안** 모바일 클릭이 필터 조건에 따라 **두 번씩** 집계됐습니다. 그 사이 일 단위 청구 금액이 이미 광고주들에게 확정·공지됐고, 한 광고주가 '내 클릭 로그와 청구 건수가 안 맞는다'고 문의해서야 알았습니다. 무엇을 바꾸나요?"

## S2. 스포츠중계 — 결승전 하프타임 광고  (핫스팟 변형)

**한 줄 요약**: 평소에는 하루 2억 클릭으로 조용하다가, 스포츠 결승전 하프타임 5분 동안 **광고 하나**에 초당 30만 클릭이 몰린다. 광고주는 그 5분을 실시간 대시보드로 본다.

| 항목 | 값 |
|---|---|
| 클릭 | 평소 하루 **2억 건**, 최대는 평균의 **5배** |
| 이벤트 시즌 | 하프타임 광고 1개에 **5분 동안 초당 30만 클릭** (다른 광고는 평소대로) |
| 광고 | **50만 개** |
| 질의 | 광고별 분 단위 클릭 수, 지난 5분 상위 100개 광고 |
| 지연 | 광고주 실시간 대시보드: **1분 안**. 과금은 다음 날 확정 |
| 보관 | 원시 데이터 **1년** |

**설계 포인트**: 교재가 "더 많은 집계 노드를 할당한다"고 짧게 넘어간 **핫스팟**이 주인공이다. `ad_id`로 파티션을 나누면 한 광고 = 한 파티션 = 한 노드라는 전제가 깨진다. 평균 QPS만 보고 노드 수를 정하면 안 되는 이유를 본다.

**돌발 상황**: "하프타임 30초 만에 하프타임 광고가 든 파티션의 소비 지연(records-lag)이 **수백만 건**으로 뛰었고, 같은 파티션에 해시된 다른 광고 수천 개의 집계도 함께 멈췄습니다. 급하게 소비자를 늘렸더니 재조정(rebalancing)으로 **3분 동안 소비 전체가 멈췄고**, 그 사이 메모리가 터진 집계 노드 하나가 재시작하면서 같은 구간을 다시 읽어 해당 광고의 클릭이 **중복 집계**됐습니다. 무엇을 바꾸나요?"

## S3. 모바일SDK — 앱 내 광고 네트워크  (늦은 이벤트 / 클라이언트 시각 변형)

**한 줄 요약**: 수천 개 앱에 심은 광고 SDK가 클릭을 보낸다. 지하철·비행기 모드에서는 단말에 모았다가 나중에 보내서 클릭의 5%가 수 분~24시간 늦게 도착한다. 단말 시계는 믿기 어렵다.

| 항목 | 값 |
|---|---|
| 클릭 | 하루 **30억 건**, 최대는 평균의 **3배** |
| 이벤트 | 기기 정보가 더 붙어 **0.2KB** |
| 늦은 도착 | 클릭의 **5%** 가 단말 버퍼에 있다가 **1분 ~ 24시간 뒤** 도착 |
| 시각 | 단말 시계가 몇 분~몇 시간 틀린 기기가 있다. 클릭 시각을 조작하는 사기 앱도 있다 |
| 질의 | 광고별 분 단위 클릭 수(앱·OS 필터), 지난 1시간 상위 100개 광고 |
| 과금 | **일 단위 정산**, 다음 날 오전 9시에 확정 |
| 보관 | 원시 데이터 **90일** |

**설계 포인트**: 교재의 "이벤트 시각 + 15초 워터마크"가 그대로 통하지 않는다. 몇 시간 늦은 5%를 버리면 청구가 5% 줄고, 기다리면 결과가 끝없이 늦어진다. **이벤트 시각 vs 처리 시각**, 워터마크 크기, 워터마크를 지난 이벤트를 어디서 메울지가 주인공이다.

**돌발 상황**: "새로 배포한 SDK 버전이 서버 응답이 늦으면 **같은 클릭을 최대 3번 재전송**하는 버그가 있었습니다. 하루 클릭이 30억 → 36억 건으로 뛰었고, 그 SDK를 쓰는 앱에 광고한 광고주들의 청구액이 **20% 늘어** 항의가 쏟아집니다. 재전송된 이벤트는 단말이 붙인 클릭 시각까지 똑같습니다. 무엇을 바꾸나요?"

## S4. RTB예산 — 실시간 입찰의 예산 소진 제어  (낮은 지연 변형)

**한 줄 요약**: 집계 결과로 광고주별 오늘 쓴 돈을 계산해, 일 예산을 다 쓰면 **10초 안에** 입찰을 멈춘다. 늦으면 예산을 넘겨 쓴 돈을 광고 플랫폼이 떠안는다.

| 항목 | 값 |
|---|---|
| 클릭 | 하루 **5억 건**, 최대는 평균의 **5배**. 평균 클릭 단가 **500원** |
| 광고주 | **10만 명**, 광고주마다 일 예산 |
| 지연 | 클릭 → 입찰 엔진의 예산 반영까지 **10초 이내** (교재는 몇 분) |
| 정확성 | 예산 초과 집행은 광고주별 **1% 이내**. 초과분은 플랫폼 부담 |
| 질의 | 광고주별 오늘 소진액(초 단위 갱신), 광고별 분 단위 클릭 수 |
| 보관 | 원시 데이터 **2년**(감사) |

**설계 포인트**: 교재 지연 요구는 "몇 분"이다. 10초가 되면 1분 윈도·워터마크·분산 트랜잭션 같은 정확성 장치들이 **모두 지연을 늘리는 쪽**이라는 게 드러난다. 빠른 값과 정확한 값을 한 경로로 낼지, 나눌지(람다식)를 본다.

**돌발 상황**: "피크 시간에 집계 노드 1대가 죽었습니다. 마지막 스냅숏이 **5분 전** 것이라 새 노드가 카프카에서 5분 치를 다시 처리하는 데 **4분**이 걸렸고, 그동안 그 노드가 맡던 광고주들의 소진액이 갱신되지 않아 일부 광고주는 예산의 **300%** 를 썼습니다. 복구 뒤에는 스냅숏 이후 구간이 두 번 반영된 광고주도 있습니다. 무엇을 바꾸나요?"

## 직접 만들기

다음 항목을 사용자와 함께 채워서 카드를 만든다. 빈 칸은 진행자가 그럴듯한 값을 제안하고 동의를 받는다.

- 무엇을 집계하나(클릭 / 노출 / 전환 / 그 밖의 이벤트) / 결과를 누가 쓰나(과금 / 입찰 / 대시보드 / 사기 탐지)
- 하루 이벤트 수, 최대 배수, 이벤트 크기, 광고(키) 수와 쏠림 정도
- 집계 단위와 질의(분 단위 수, 상위 N개, 필터 차원)
- 지연 목표, 늦게 도착하는 이벤트의 비율과 최대 지연, 타임스탬프를 누가 찍나
- 정확성 요구(오차가 돈인가), 원시 데이터 보관 기간
- 돌발 상황 1개 (진행자가 만들되, 시나리오의 가장 약한 가정을 깨는 것으로)

## 랜덤

S1~S4 중 하나를 무작위로 고른다. 입문자라면 S1을 권한다.
