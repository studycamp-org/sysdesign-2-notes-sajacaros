# 학습 내용 요약 (진행자 참고용)

출처: 「가상 면접 사례로 배우는 대규모 시스템 설계 기초 2」 6장 광고 클릭 이벤트 집계, 스터디 정리본 `06_광고클릭_이벤트집계_설계.md`, `06_부록_집계윈도_알고리즘.md`.
`힌트` 응답, 피드백, 결과 문서의 "교재와 다르게 간 곳" 섹션에 쓴다. 답하기 전에 기준안을 먼저 말하지 않는다.
`(보충)` 표시는 정리본에 없어 교재·일반 지식으로 채운 부분이다.

- 교재 밖 기술 예시: Apache Flink(이벤트 시각 처리, 워터마크, 체크포인트 기반 정확히 한 번, 허용 지연(allowed lateness)·사이드 출력), Kafka Streams, Kafka 트랜잭션·멱등 생산자, Spark Structured Streaming, Apache Beam/Dataflow, ClickHouse·Druid·Pinot(실시간 OLAP), Hive, Elasticsearch, Parquet·ORC(열 지향 파일), HyperLogLog(고유 사용자 수 근사), Count-Min Sketch(상위 N 근사), 클릭 ID 기반 중복 제거, 키 솔팅(핫 키에 접미사), Yelp의 정확히 한 번 사례

## 1. 요구사항 (교재 기준안)

- 기능: 지난 M분 동안 특정 광고(`ad_id`)의 **클릭 수 집계** / 매분 가장 많이 클릭된 **상위 100개 광고** / 다양한 속성(국가 등)에 따른 **필터링**.
- 비기능: **정확성**(RTB·광고 과금에 쓰임) / **지연·중복 이벤트를 적절히 처리** / 부분 장애를 견디는 **안정성** / 종단 지연은 **몇 분 이내**.
- 추정: 하루 클릭 **10억 건**, 광고 **200만 개**, 평균 **10,000 QPS**, 최대 **50,000 QPS**(평균의 5배). 이벤트 1개 **0.1KB** → 하루 **100GB**, 한 달 **3TB**. (보충) 사업은 매년 30% 성장, 트래픽은 3년마다 두 배.

## 2. 개략적 설계 (보충: 정리본은 목차만 있어 교재로 채움)

- **질의 API** (보충): ① `GET /v1/ads/{ad_id}/aggregated_count?from&to&filter` — 지난 M분 클릭 수 ② `GET /v1/ads/popular_ads?count&window&filter` — 지난 M분 상위 N개 광고.
- **원시 데이터** (보충): `ad_id, click_timestamp, user_id, ip, country`. **집계 결과 데이터**: `ad_id, click_minute, count` (+ 필터용 `filter_id`), 상위 N개는 `window_size, update_time_minute, most_clicked_ads`.
- **원시 vs 집계 비교** (보충): 원시는 전체 데이터 보관·필터링과 재계산 가능하지만 저장량이 크고 질의가 느리다. 집계는 작고 빠르지만 손실이 있다(10개가 1개로). → **둘 다 저장**: 원시는 백업과 재계산용(오래된 것은 냉동 저장소로), 집계는 질의용.
- **데이터베이스 선택** (보충): 쓰기 중심(최대 5만 QPS), 시간 범위 질의 → **카산드라** 같은 NoSQL, 또는 원시 데이터를 S3에 ORC·파케이·AVRO 같은 열 지향 형식으로. 집계 결과도 같은 DB 가능(읽기·쓰기 모두 있음).
- **비동기 처리** (보충): 생산자와 소비자의 처리 용량이 달라 동기로 묶으면 소비자가 터진다 → 메시지 큐로 분리. 로그 모니터 → **카프카 ①**(원시 클릭) → 집계 서비스 → **카프카 ②**(집계 결과) → DB 기록 프로세스 → 집계 결과 DB. 카프카 ① → DB 기록 프로세스 → 원시 데이터 DB. 두 번째 카프카는 **정확히 한 번**(원자적 커밋)을 위해 둔다.
- **맵리듀스** (보충): 집계 서비스는 DAG — 맵 노드(`ad_id % 3` 등으로 나눠 보냄, 카프카 파티션이 이미 나눠 줄 수도 있지만 정제·변환을 맡음) → 집계 노드(메모리에서 분당 `ad_id` 클릭 수, 상위 N은 힙) → 리듀스 노드(여러 집계 노드의 상위 100을 합쳐 최종 100).
- **핵심 3개 용례** (보충): ① 클릭 수 집계(`ad_id`로 맵 → 집계 노드가 분당 카운트) ② 상위 N개(집계 노드마다 지역 상위 3 → 리듀스에서 전역 상위 3) ③ 필터링: **스타 스키마**처럼 국가·기기 등 필터 조합을 미리 정의해 그 단위로 미리 집계(사실 테이블과 차원). 이해하기 쉽고 결과를 재사용하지만 필터 조합만큼 버킷·레코드가 늘어난다.

## 3. 상세 설계

### 스트리밍 vs 일괄 처리
- 스트림: 데이터를 오는 대로 처리해 거의 실시간 결과. 일괄: 이력 데이터 백업·재처리에 활용.
- **표 6.17**: 서비스(온라인) — 응답성·가용성·지연, 입력은 사용자 요청 / 일괄(오프라인) — 응답 불필요, 유한 입력, 처리량 기준, 맵리듀스 / 스트리밍 — 응답 불필요, **무한 입력**, 처리량 + 지연 기준, 플링크.
- **람다**: 일괄 경로 + 스트리밍 경로를 동시에 → **코드가 두 벌**. **카파**: 하나의 스트림 엔진으로 실시간 처리와 재처리를 모두. **교재는 카파**.
- **데이터 재계산(그림 6.11)**: 집계 버그 발견 → 재계산 서비스가 원시 데이터 저장소에서 읽음(일괄) → **재계산 전용** 집계 서비스(실시간과 간섭 방지) → 두 번째 메시지 큐 → 집계 결과 DB.

### 시간
- 이벤트 시각(클릭 발생) vs 처리 시각(집계 서버). 메시지 큐·네트워크 때문에 격차가 커질 수 있다(그림 6.12: 5시간 늦게 도착).
- **표 6.18**: 이벤트 시각 — 정확하지만 클라이언트 타임스탬프에 의존(시각 오류·조작). 처리 시각 — 안정적이지만 늦게 오면 부정확. → **이벤트 시각 추천** + 워터마크.
- **워터마크**: 1분 텀블링 윈도에서 윈도 끝 직후 도착한 이벤트가 누락(그림 6.13) → 윈도에 여분 구간(예: 15초)을 붙인다(그림 6.14). 길면 정확하지만 늦고, 짧으면 빠르지만 부정확. 아주 늦게 오는 이벤트는 못 잡는다 → 발생 확률이 낮아 복잡하게 만드는 ROI가 낮고, **하루 마감 조정**으로 보정.

### 집계 윈도 (부록 참고)
- 텀블링(고정): 같은 크기, 겹치지 않음, 이벤트는 정확히 1개 윈도. `윈도 시작 = floor(시각/크기) × 크기`. → **매분 클릭 수**(그림 6.15).
- 호핑: 크기 고정, hop < 크기라 겹침. 이벤트가 `크기 ÷ hop`개 윈도에. 1분 텀블링 결과 여러 개를 합쳐 구현. 플링크는 이걸 "sliding window"라 부르고, 책 그림 6.16(3분 길이, 1분 이동)도 엄밀히는 호핑.
- 슬라이딩: 이벤트 시각 기준으로 미끄러지며 겹침. → **지난 M분 상위 N개**(그림 6.16).
- 세션: 비활동 간격(gap)으로 나뉘는 가변 크기. 사용자 세션·체류 시간 분석.

### 전달 보장
- 집계 결과는 과금에 쓰이므로 **중복 없이, 빠짐없이**. 최대 한 번 / 최소 한 번 / 정확히 한 번. 약간의 중복이 괜찮으면 최소 한 번이 보통이지만, 여기선 몇 퍼센트가 수백만 달러 → **정확히 한 번**(Yelp 사례).
- 중복 원인: 클라이언트가 같은 이벤트를 여러 번 보냄(악의적이면 광고 사기·위험 제어) / 서버 장애로 업스트림에 오프셋을 못 알려 재소비(그림 6.17: 오프셋 100~110 집계·전송 후 6단계 전에 장애 → 100부터 다시).
- 해결 1(그림 6.18): HDFS/S3에 오프셋 기록, 저장된 오프셋으로 이미 처리한 건 무시. 하지만 다운스트림 전송 **전에** 저장하면 그 직후 장애 시 **유실**.
- 해결 2(그림 6.19): 다운스트림 수신 확인 **후에** 오프셋 저장 → 유실은 없고 다시 보낼 수 있다(중복 가능).
- 해결 3(그림 6.20): 집계 결과 전송 · 오프셋 저장 · 수신 확인을 **하나의 분산 트랜잭션**으로 → 정확히 한 번. 대규모에서 아주 어렵다.

### 규모 확장
- 메시지 큐·집계 서버·DB는 결합도가 낮아 **각자** 확장.
- 메시지 큐: 생산자는 쉽게 확장. 소비자는 소비자 그룹 **재조정**(소비자 수백 개면 수 분 → 한가한 시간에). 브로커: 해시 키 `ad_id`(같은 광고는 같은 파티션), **파티션 수는 미리 넉넉히**(늘리면 같은 `ad_id`가 다른 파티션으로), 토픽의 물리적 샤딩(지역별·사업 유형별 → 대역폭↑, 재조정 시간↓ / 복잡성·운영비↑).
- 집계 서비스: 본질적으로 맵리듀스(그림 6.22). 대역폭 올리기 — 방안 1: `ad_id`마다 스레드(다중 스레드, 구현 쉬움) / 방안 2: 하둡 YARN 같은 **자원 공급자**에 배포(다중 프로세싱, 실제로 더 많이 씀).
- DB: 카산드라는 안정 해시 비슷한 방식으로 수평 확장 기본 지원, **가상 노드**로 새 노드 추가 시 자동 균형(그림 6.24).
- **핫스팟**: 큰 광고주 광고에 클릭이 몰림 + `ad_id` 파티션 → 특정 노드 과부하. 완화(그림 6.25): 감당량 초과 → 자원 관리자에 추가 자원 요청 → 노드 추가 할당 → 원래 노드가 이벤트를 나눠 보냄 → 축약 결과를 원래 노드에 기록. 더 복잡한 방법: **전역-지역 집계**, **분할 고유 집계**.

### 결함 내성
- 집계는 메모리라 노드 장애 시 손실 → 업스트림 카프카에서 다시 받아 재생성 가능. 처음부터는 오래 걸림 → 업스트림 오프셋과 지난 M분 상위 N개 같은 **시스템 상태를 스냅숏**(그림 6.26).
- 복구(그림 6.27): 새 노드가 마지막 **점진적 스냅숏**에서 복구 + 스냅숏 이후 이벤트는 카프카에서 다시 처리.

### 데이터 모니터링 및 정확성
- 결과가 RTB·청구서에 쓰이므로 중요. 지표: **지연 시간**(구간마다 타임스탬프), **메시지 큐 크기**(카프카 records-lag, 늘면 집계 노드 추가), 집계 노드 자원(CPU·디스크·JVM).
- **조정**: 은행과 달리 비교할 제3자가 없다 → 매일 각 파티션의 클릭을 **이벤트 시각 순으로 일괄 처리한 결과**와 실시간 결과를 비교. 더 정밀하게는 더 작은 윈도(예: 1시간). 늦은 이벤트 때문에 정확히 일치하지 않을 수 있다.
- **최종 설계안(그림 6.28)**: 로그 모니터 → 메시지 큐 → 집계 서비스 / DB 기록 → 원시 DB. 집계 결과 → 메시지 큐 → DB 기록 → 집계 결과 DB ← 질의 서비스(대시보드). 재계산 서비스 → 원시 DB → 재계산 전용 집계 서비스 → 메시지 큐. **조정**이 원시 DB와 집계 결과 DB를 비교.

### 대안적 설계안 (그림 6.29)
- 면접에서는 전문 소프트웨어 내부보다 사고 과정과 트레이드오프 설명이 중요.
- 로그 모니터 → 메시지 큐 → **위험성 통제 엔진** → 하이브(+ 빠른 질의는 일래스틱서치) / **클릭하우스·드루이드** 같은 OLAP DB로 집계. 고객 대상 애널리틱스는 클릭하우스, 데이터 과학자는 일래스틱서치.

## 시나리오별로 교재 기준안이 흔들리는 지점

| 시나리오 | 교재 가정이 깨지는 곳 | 검토할 만한 대안 |
|---|---|---|
| S1 검색광고 | 거의 없음. 원시 1년 보관, 일 단위 청구 확정 | 교재 그대로(카파, 이벤트 시각 + 워터마크, 정확히 한 번, 일 단위 조정)가 충분. 돌발은 **재계산 전용 경로**로 3일 치를 다시 계산해 덮어쓰고, 확정 청구는 정정 이벤트로 처리. "왜 3일 뒤에 알았나" → 조정을 일 단위로 돌려 실시간과 일괄 결과 차이에 경보, 배포 전후 비교(카나리) |
| S2 스포츠중계 | 광고 하나에 초당 30만 → `ad_id` 파티션 하나가 30배 초과 | 미리 알려진 핫 광고는 키에 접미사를 붙여(`ad_id#0..31`) 여러 파티션에 흩고 리듀스에서 합침(전역-지역 집계), 자원 공급자로 노드 탄력 할당(그림 6.25). 파티션·소비자는 이벤트 전에 미리 늘려 재조정을 피크 밖에서. 돌발은 핫 키 분산 + 협력적 재조정(교재 밖) + 정확히 한 번(재시작 중복 방지) |
| S3 모바일SDK | 5%가 최대 24시간 늦게, 단말 시계 불신, 클라이언트 재전송 | 이벤트 시각은 쓰되 서버 수신 시각과 차이가 크면 보정·격리. 실시간은 짧은 워터마크로 빠르게, **일 정산은 원시 데이터 일괄 재집계로 확정**(람다식 이원화 또는 카파 + 하루 마감 재계산). 돌발은 오프셋 기반 정확히 한 번으로는 못 막음 → **클릭 ID**(SDK가 클릭마다 UUID)로 중복 제거, 위험 제어 컴포넌트 |
| S4 RTB예산 | 지연 10초, 초과 집행이 곧 손실 | 예산 소진은 **빠른 근사 경로**(짧은 윈도, 처리 시각 또는 아주 짧은 워터마크, 최소 한 번 + 멱등)로 입찰 엔진에 보내고, 청구는 정확한 경로(정확히 한 번 + 조정)로 따로. 예산 여유분을 남기고 미리 감속(pacing). 돌발은 스냅숏 주기 단축(분 → 초 단위 체크포인트), 대기 노드(핫 스탠바이), 복구 중엔 해당 광고주 입찰 보수적으로 감속, 멱등 쓰기로 이중 반영 방지 |
