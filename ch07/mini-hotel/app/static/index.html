교재 그림 4·5의 구성을 그대로 컨테이너로 띄웠습니다. 요청이 지나간 상자와 선은 노랗게 표시되고, 다음 액션이 올 때까지 그대로 남습니다. PostgreSQL 은 인스턴스 하나지만 서비스마다 스키마와 계정을 따로 둬서, 다른 서비스의 테이블은 읽지도 쓰지도 못합니다. 샤딩은 하지 않았습니다(hash(hotel_id) % N, 여기서는 N = 1).

room_type_inventory 행(DB)과 Redis 캐시 값을 나란히 봅니다. 한도 = total_inventory × (100 + 초과 예약%) 내림. 노란 칸은 캐시와 DB가 다른 곳, 빨간 줄은 한도를 넘겨 판 날(이중 예약)입니다.

① 마지막 방을 여러 명이 동시에 경쟁 조건 · 그림 11
  1. 지금 보고 있는 호텔·객실 유형·날짜(재고 탭 선택)의 남은 객실을 1개로 만들고
  2. 봇 N명이 각자 예약창을 연 뒤 동시에 "예약 완료"를 누릅니다.

잠금 없음 + 경쟁 구간 500ms 로 먼저 해 보고, 락 방식을 바꿔 가며 다시 해 보세요.

② 같은 사람이 버튼을 두 번 멱등 키 · 그림 7·10
  1. 위 설정에서 버튼 중복 클릭을 끄고
  2. 예약창에서 "예약 완료"를 빠르게 두 번 누릅니다.

요청은 두 번 가지만 같은 reservation_id 라서 두 번째는 기본 키 유니크 제약에 걸립니다. 흐름 탭에서 확인하세요.

③ 캐시와 DB가 어긋날 때 그림 16
  1. 캐시 반영 지연을 10초로 두고, 탭 두 개를 다른 사람으로 엽니다.
  2. 남은 객실 1개인 방을 탭 A에서 예약 → 탭 B는 10초 동안 여전히 "1개 남음"을 봅니다.
  3. 탭 B가 예약하면 캐시는 통과하지만 DB 가 최종 검사에서 막습니다.
④ 결제는 됐는데 알림이 사라지면 서비스 간 일관성 · 그림 19
  1. 결제를 결제 후 알림 유실, 결제 대기 한도를 30초로 두고 예약·결제합니다.
  2. 돈은 빠져나갔는데 예약은 pending → 30초 뒤 만료되어 cancelled.
  3. 결제를 성공으로 되돌리면 Payment Service 가 알림을 다시 보내고, 예약이 이미 끝났으니 보상 트랜잭션으로 환불합니다.
⑤ 서비스 경계 그림 17

Payment Service 계정으로 reservation.reservation 을 직접 UPDATE 해 봅니다. 스키마 권한이 없어 막힙니다. 그래서 결제 결과는 API 로 알려야 하고, 한 트랜잭션으로 묶을 수 없습니다.

예약·결제를 모두 지우고 재고를 처음 상태로 되돌립니다. 설정은 유지됩니다.
