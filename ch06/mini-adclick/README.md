# mini-adclick — 6장의 문제를 직접 일으켜 보는 광고 클릭 집계 실험실

데이터가 많다는 흉내는 내지 않는다. **사람이 휴대폰(브라우저)으로 광고를 누르고, 네트워크와 서버에 문제를 일으키면**
6장 3단계의 장치들이 어떻게 대응하는지 클릭 하나 단위로 본다.

구성도: [`../demo-architecture.html`](../demo-architecture.html)

```
 휴대폰(탭) ──HTTP──▶ 광고 서버(api) ──clicks.log──▶ Fluent Bit ──▶ Kafka raw-clicks ──▶ 집계 서비스
  ✈ 비행기 모드         · 정답 장부                                                      │ 10초 윈도 · 워터마크
  📶 불안정 네트워크     · 1초 tick                                                       │ 중복 제거 · 전달 보장 ①②③
                                                                                         ▼ 스냅숏 · 재계산
                     ClickHouse ◀── Kafka 엔진 + MV ◀── Kafka agg-results ◀──────────────┘
                         ▲  (증가분을 더한다)
                         │ 보정
 RustFS (Parquet) ◀── archiver ◀── raw-clicks          recon (DuckDB 재집계 검증) ──┘
```

## 실행

```bash
./run.sh                  # 빌드하고 띄운다 → http://localhost:8006
docker compose down -v    # 끝. Kafka·ClickHouse·RustFS 는 메모리(tmpfs)에만 있어 사라진다
```

탭을 여러 개 열면 휴대폰이 여러 대가 된다. 스터디에서 각자 노트북으로 같은 주소에 붙어도 된다.

## 축소한 것

| 교재 | 여기 | 이유 |
|---|---|---|
| 1분 텀블링 윈도 | **10초** | 결과를 1분씩 기다리면 실험이 안 된다 |
| 워터마크 15초 | **3초** (0~10초 조절) | 같은 이유 |
| 하루 10억 건 | 사람이 누른 만큼 | 문제를 보이는 게 목적 |
| 일일 재집계 검증 | 버튼 | |

## 실험 (화면 위 '실험 순서'와 같다)

| # | 교재 | 하는 것 | 보이는 것 |
|---|---|---|---|
| 1 | — | 광고 몇 번 누르기 | 점이 윈도 안에 찍히고, 닫히면 장부 = 집계 ✓ |
| 2 | 이벤트 시각 vs 처리 시각 (그림 12) | ✈ 켜고 누른 뒤 8초쯤 있다가 끄기 | 점은 누른 시각에, 점선이 도착 시각으로. 처리 시각 열은 다른 윈도에 센다 (≠) |
| 3 | 워터마크 (그림 13·14) | 워터마크 0초 + 2~3초 ✈ → 5초로 올리고 다시 | 0초면 ✗ 버림(−1), 5초면 잡힘. 대신 '워터마크 대기'가 길어진다 |
| 4 | 아주 늦은 이벤트 + 재집계 검증 (그림 28) | ✈ 30초 넘게 → 🔍 재집계 검증 | ✗ 버림 → 장부보다 모자람 → DuckDB 가 원본에서 찾아 '보정 +1' |
| 5 | 클라이언트 중복 | 📶 불안정한 네트워크 켜고 누르기 | 응답 유실로 재전송(↻2, ↻3) → 같은 click_id 는 한 번만 |
| 6 | 서버 장애: 유실·중복 (그림 17~20) | 전략 ①②③ 중 하나 → 💥 장전 → 광고 누르기 | ① 오프셋 먼저: **−N 유실**, 점이 회색 / ② 전송 먼저: **+N 중복**, 점이 ×2 / ③ 트랜잭션: **✓** |
| 7 | 스냅숏 (그림 26·27) | ③에서 스냅숏 켬/끔 → 💥 | 기록: '스냅숏에서 복구' vs '처음부터 N건 다시 읽어 복구'. 결과는 둘 다 정확, 복구 비용이 다르다 |
| 8 | 버그 배포 → 재계산 (그림 11) | 🐞 배포 → 누르기 → ✅ 수정 → 🔁 재계산 | 버그 동안 +N(2배) → 재계산이 닫힌 윈도를 원본부터 다시 집계해 갈아 끼움 |

### 확인한 결과 (2026-11-21, 스크립트로 휴대폰 흉내)

| 시나리오 | 장부 | 이벤트 시각 집계 | 처리 시각 집계 |
|---|---|---|---|
| 정상 3건 + 같은 click_id 재전송 1건 | 4 | 4 ✓ | 4 |
| 윈도 끝 2초 뒤 도착, 워터마크 3초 | 2 | 2 ✓ | 1 (다른 윈도에 셈) |
| 같은 상황, 워터마크 0초 | 2 | 1 (−1) | 1 |
| 40초 늦게 도착 | 1 | 0 (−1) → 재집계 검증 보정 +1 | 0 |
| ① 오프셋 먼저 + 💥 | 4 | 0 (−4 유실) | 0 |
| ② 전송 먼저 + 💥 | 4 | 7 (+3 중복) | 7 |
| ③ 트랜잭션 + 💥 | 4 | 4 ✓ | 4 |
| ③ 스냅숏 끔 + 💥 | 3 | 3 ✓ (처음부터 290건 다시 읽어 복구) | 3 |
| 🐞 버그 버전 | 3 | 6 (+3) → 🔁 재계산 후 3 ✓ | 3 |

재계산은 ①②로 망가진 윈도까지 원본에서 다시 맞춘다. 대신 아주 늦은 클릭은 같은 워터마크 규칙으로 다시 버려지므로,
재계산 뒤에도 재집계 검증이 필요하다 (교재: 실시간 경로는 카파, 검증은 배치).

## 구성 요소

| 구성 요소 | 파일 | 하는 일 |
|---|---|---|
| api (광고 서버) | `app/api.py`, `app/static/index.html` | 휴대폰 클릭 수신 → `clicks.log`, 정답 장부, 1초 tick, 운영 설정, 화면 |
| fluent-bit | `fluent-bit/fluent-bit.yaml` | Log Watcher: tail → Kafka `raw-clicks` |
| kafka / kafka-init | (compose) | Apache Kafka 4.1 KRaft. `raw-clicks`(1 파티션), `agg-results`, `agg-snapshots`(compact) |
| aggregator | `app/aggregator.py` | 10초 윈도·워터마크·중복 제거·처리 시각 집계, 전달 보장 ①②③, 스냅숏 복구 / 재생 복구, 💥, 재계산 |
| clickhouse | `clickhouse/init.sql` | Kafka 엔진 → MV → MergeTree. 증가분을 더한다 |
| archiver | `app/archiver.py` | `raw-clicks` → Parquet → RustFS (3초마다, 최소 한 번) |
| recon | `app/recon.py` | DuckDB 로 Parquet 원본을 click_id 기준으로 다시 세어 ClickHouse 와 비교, 차이만큼 보정 |

### 설계 메모

- **집계 DB 는 '더하기'다.** 집계 서비스는 배치마다 (윈도, 광고)별 증가분을 보낸다. 덮어쓰기(Replacing) 방식이면
  같은 결과가 두 번 와도 티가 안 나서 그림 19의 중복을 볼 수 없다.
- **tick.** 클릭이 드물면 이벤트 시각이 안 흘러 윈도가 안 닫힌다. 광고 서버가 1초마다 '지금 시각'을 로그에 넣어
  워터마크를 민다 (Flink 의 주기적 워터마크·idle source 처리와 같은 역할).
- **판정은 결과를 내보낸 뒤에 알린다.** 화면의 점 색은 '집계 DB 로 결과가 나갔는가'를 뜻한다. ①에서 💥 로 잃은 클릭은
  끝까지 회색으로 남는다.
- **③의 스냅숏은 오프셋과 같은 트랜잭션에 들어간다.** 복구할 때 스냅숏의 오프셋이 커밋된 오프셋과 다르면 버리고
  처음부터 다시 읽는다.

## 교재와 다른 점

- Cassandra → **ClickHouse**, Database Writer → **Kafka 엔진 + MV**.
- 집계 서비스는 한 프로세스. Map/Aggregate/Reduce 노드 분산과 핫스팟은 다루지 않았다.
- top N, 필터(국가·IP)는 뺐다. 이 데모는 3단계의 정확성 문제에 집중한다.
