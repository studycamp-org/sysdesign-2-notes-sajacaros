광고 클릭 이벤트 집계 — 문제를 직접 일으켜 보는 데모

데이터 양은 흉내 내지 않는다. 사람이 휴대폰으로 광고를 누르고 네트워크·서버에 문제를 일으키면, 6장의 장치(이벤트 시각·워터마크·중복 제거·정확히 한 번·스냅숏·재계산·재집계 검증)가 어떻게 대응하는지 클릭 하나 단위로 본다.

Apache Flink가 맡는 일

교재의 Aggregation Service

  • Flink SQL 하나: TUMBLE(…, INTERVAL '10' SECOND) 윈도에 COUNT(DISTINCT click_id), WATERMARK FOR ts AS ts - INTERVAL 'N' SECOND.
  • 체크포인트 = 교재의 스냅숏(윈도 상태 + Kafka 오프셋). TaskManager 가 죽으면 마지막 체크포인트에서 스스로 복구.
  • Kafka 싱크 보장 NONE / AT_LEAST_ONCE / EXACTLY_ONCE(체크포인트에 묶인 2단계 커밋) = 교재 해법 1·2·3.
  • 설정 변경·버그 배포는 세이브포인트로 잡 교체, 재계산은 같은 SQL 의 유한(bounded) 잡 (카파).

ClickHouse가 맡는 일

Database Writer가 따로 필요 없다

  • Kafka 엔진 테이블이 agg-results 토픽을 직접 구독한다. 교재의 Database Writer 역할이다.
  • Materialized View가 들어온 행을 받아 실제 저장 테이블로 옮긴다.
  • 저장 테이블은 MergeTree이고 질의는 늘 sum(clicks). Flink 가 같은 윈도 결과를 두 번 내면 값이 실제로 커진다 — 교재 그림 19의 중복이 숫자로 보인다.
  • 재집계 검증의 보정도 차이만큼의 증가분 행이고, 재계산은 닫힌 윈도의 행을 지우고 다시 넣는다.

데모 시나리오

사용자가 문제를 일으킨다

  1. ✈ 비행기 모드 → 이벤트 시각 vs 처리 시각 (그림 12)
  2. 워터마크 0~10초 조절 → 늦은 클릭이 잡히거나 버려짐 (그림 13·14)
  3. 아주 늦은 클릭 → 버려짐 → DuckDB 재집계 검증이 보정 (그림 28)
  4. 📶 불안정한 네트워크 → 재전송 중복 → click_id로 한 번만
  5. 전달 보장 ①②③ + 💥(TaskManager 강제 종료) → 유실 / 중복 / 정확 (그림 18~20)
  6. 체크포인트 켬·끔 + 💥 → 체크포인트 복구 vs 처음부터 재생 (그림 26·27)
  7. 🐞 버그 배포(세이브포인트) → 🔁 재계산(유한 잡) (그림 11, 카파)
