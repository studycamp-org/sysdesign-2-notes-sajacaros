# mini-monitor 시연 시나리오

약 3분. `./run.sh` 로 띄운 뒤 1~2분 지나 데이터가 쌓이면 시작한다.
영상: `media/시연_전체흐름.mp4` (다시 찍기: `node media/record.cjs <출력 폴더>`)

| # | 화면 | 하는 것 | 보여 줄 것 (교재) |
|---|---|---|---|
| 0 | 파이프라인 `/` | 전체 훑기 | ① 출처 → ② 수집기 → ③ Kafka → ④ writer → ⑤ TimescaleDB → ⑥ 질의 서비스 → ⑦ 경보 (그림 22) |
| 1 | 파이프라인 | push 카드 `service:web` 의 **+** | 컨테이너 생성 → "기동 중" → 서비스 탐색 등록 → 정상 행 |
| 2 | 파이프라인 | pull 카드 `service:api` 의 **+** | 새 pull 대상이 해시 링에 올라가 수집기 담당이 다시 나뉨 (그림 11) |
| 3 | 파이프라인 → 호스트 맵 `/hosts` | `push-1` 행의 🔥 | 시뮬레이터가 나쁜 값을 만들어 평소 경로로 보냄. 호스트 맵(질의 서비스 경유)에서 해당 칸이 빨개짐 |
| 4 | 경보 `/alerts` | 기다림 | `high_cpu`·`high_latency` 가 pending → (for 15초) → firing, host 별로 병합된 알림 1건 (그림 19·20) |
| 5 | 파이프라인 | writer 카드 **DB 장애** → **재개** | 쓰기를 멈추면 Kafka 파티션에 빨간 lag 가 쌓이고, 재개하면 따라잡아 0. 잃는 데이터 없음 (그림 15) |
| 6 | SLO `/slo` | 장애 주입: 🔥 · 전체 · 100% · 3분 | 응답 지연 SLO 의 5분 소진율이 뛰어 "빠르게 소진" / "위반", 오류 예산 감소 |
| 7 | Grafana | 대시보드 훑기 | 지표 패널은 질의 서비스(Prometheus 호환)를 거쳐 그린다 |

정리: SLO 페이지 **모두 정상으로**, 1·2에서 늘린 에이전트는 같은 그룹의 **−** 로 되돌린다.

## 말로 할 것

- **0** 시뮬레이터 = 모니터링 대상 서버. push 는 에이전트가 보내고, pull 은 수집기가 긁어 간다.
- **1** 컨테이너가 떠도 서비스 탐색에 등록돼야 시스템이 안다.
- **2** 수집기들은 서로 대화하지 않고 같은 해시 링 계산으로 담당을 나눈다. 가상 노드 16개라 고르게 나뉜다.
- **3** 장애 버튼은 파이프라인에 메시지를 끼워 넣는 게 아니라 서버 자체를 아프게 만든다.
- **4** 경보 관리자는 5초마다 규칙의 expr 를 질의 서비스에 묻는다. for 동안 이어져야 firing.
- **5** writer 는 DB 에 쓴 뒤에야 커밋한다. 그래서 DB 가 멈춰도 데이터는 Kafka 에 남는다.
- **6** 경보는 "지금 무엇이 깨졌나", SLO 는 "예산이 얼마나 남았나". 실습이라 창은 1시간.
- **7** Grafana 는 TSDB 가 TimescaleDB 라는 걸 모른다. 질의 서비스가 둘을 분리한다.
